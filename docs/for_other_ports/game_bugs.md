# Bugs every port inherits

Bugs we found or fixed in Halo CE as the decomp reproduces it, and in ChupathingyCE's platform layer, that matter beyond the PSP. Engine at ChupathingyCE `v0.7.5d` (`d98982b8`); each was checked there [D] unless it says otherwise. Labels: [M] PSP, [E] emulator, [D] code or data, [U] inference.

**Upstream?** CLAUDE.md lets us offer ChupathingyCE only small, self-contained changes that the maintainer can explain line by line and that were tested on its desktop build. "Candidate" below means the change is that shape; nothing has been offered, and nothing is promised.

## 1. In the original game (the decomp keeps them)

| # | Bug | Symptom | Cause | Our fix, where | Upstream? |
|---|---|---|---|---|---|
| G1 | **`location.bonus` is stack garbage** | Invisible in play. Two runs or two builds that should match don't: state hashes, sleep checksums and any memo keyed on an object's location differ | `struct location`'s last word is written in play only by `scenario_location_award_bonus` (to NONE). Every other location is built on the stack without it and copied into objects, actors and props [D] | Set to NONE where an object's location is stored. With it, b30 plays identically in every pool across two builds [E]. `FIXES_BONUS` (`objects.c#bonus`), keep word `bonusold`; `review_b138.md` | Candidate (one line, no play change) |
| G2 | **A new weapon "tracks" object slot 0** | Every ground weapon looks as if it is tracking something; anything that reasons about a weapon's state is misled | `weapon_new` never sets `tracked_object_index`; it keeps the datum's 0. Index 0 with identifier 0 reads as "any" to `datum_try_and_get`, so it finds whatever holds slot 0 and `weapon_update`'s existence check never clears it [D] | **Not changed** (the desktop servers run the same code, and fixing it changes a weapon's state from its first tick). Our sleep rule reads the check's answer instead, so ground weapons can sleep: b122's beach weapons cost 5.1 ms a tick before [M]. `FIXES_123L` (`objects.c#weapontrack`); `review_b123_lititems.md` §4, `review_b124.md` | Candidate as a report, not a patch (it changes play) |
| G3 | **The HUD's weapon state is half uninitialised** | The HUD's secondary-weapon warnings, the empty-secondary sound and the swap prompt's "depleted" test can fire on a one-magazine weapon, differently from build to build | Every caller keeps the state on the stack unset; `weapon_build_weapon_interface_state` fills only the weapon's own magazines [D] | Zero the state first. **DamnationCE's fix** (xshxdex98, CC0, `488bd83e`), found through halo-ce-vita's notes. `FIXES_126` (`weapons.c#interfacestate`), keep word `weaponstateold`; `review_b126.md` | Candidate (DamnationCE's, CC0) |
| G4 | **Crouch and zoom prompts are crossed** | A prompt that names crouch shows the zoom button, and the reverse | `button_mappings` (`hud_messaging.c`, `ui_widget.c`) sends the crouch token to control 11 and zoom to 10; `input_abstraction.c` binds 10 to crouch and 11 to zoom [D]. The decomp matches the binary, so the Xbox does it too [U] | **Not changed**: correcting it departs from the original's data (the maintainer's call). It only shows if a map's strings use those tokens [U]. `review_controls.md`, "Open" | Report only |
| G5 | **A corpse's aim never settles** | Not visible. Defeats any "skip objects that didn't change" scheme for bodies | The aiming and looking servos keep running on a dead unit and overshoot between two values every tick (aiming and looking vectors and velocities flip) [E]. A dying unit's pose ignores them [D] | Our corpse checksum leaves those words out; a sleeping corpse keeps its last values. `FIXES_106` (`units.c#aim`) | No (it's behaviour, harmless where nobody sleeps objects) |
| G6 | **The main menu rewrites 26 game-variant files on every start** | On slow storage, a long wait before the menu takes input: ~54 s on our PSP-1000, nearly all of it this [M] | The saved-game check empties the default playlist folder and writes every default variant again, each start | A variant whose file already holds the same bytes is left alone, so only a fresh card writes them. `FIXES_FRONT` (`playlist_profile.c#variants`), keep word `variantswrite` | Candidate |
| G7 | **A full sound cache writes a debug dump mid-frame** | A hitch of a Memory Stick write (several hundred lines) up to once every 10 s; 7 times in one b30 run [E] | The Xbox's debug dump on a cache failure is still compiled in | Left out on the PSP; the failure is still logged. `FIXES_SOUND` (`xbox_sound_cache.c#nostabbed`); commit `b83b8fa` | Maybe (behind a platform switch) |
| G8 | **The frame throttle busy-waits on the vertical blank** | Where a thread moves the blank count: the game gives up its frame-rate control after a second (the red "stuck waiting for VBLANK callback!"), and a core burns while it waits | `main_rasterizer_throttle` (`main.c`) loops on the blank count and sleeps only while the cache precaches [D]. A PSP thread runs until it waits, so the spinning game thread kept the port's blank thread from running [M] | A millisecond's sleep each turn of the loop. `FIXES_36` (`main.c`), b41. halo-ce-vita met it too (10–20 ms a frame, its `main.c` comment) and caps its frames by sleeping instead | Maybe (desktop builds pace by vsync) |

## 2. Off x86 only (MIPS, ARM, SH-4: the Xbox forgave them)

| # | Bug | Symptom | Cause | Our fix, where | Upstream? |
|---|---|---|---|---|---|
| X1 | **FPU traps** | The first tick of Blood Gulch freezes the PSP and powers it off | The game divides by a unit's `aiming_velocity_maximum`, which is 0 for some units; 0/0 is an invalid operation. A PSP thread starts with overflow, divide-by-zero and invalid traps enabled; the Xbox masks them [M] | Every thread masks them at start (`psp_fpu_mask_traps`, `psp/src/psp_platform.c`; the game's threads through `xbox_kernel.c`). The emulator doesn't take FPU traps, so only hardware showed it [M] | No (platform layer) |
| X2 | **NaN to integer differs** (the same 0/0) | A still unit's "aiming change" function reads full speed: any shader or animation driven by it moves | x86 turns NaN into 0x80000000, so the byte is 0; the PSP's FPU gives 0x7FFFFFFF, so 255 [D]. ARM gives 0 like x86, so only MIPS ports diverge (`research_vita.md` §6) | Spell out x86's answers. **Halo 64's fix** (JackTulli, CC0; `research_halo64.md` H1). `FIXES_126` (`units.c#aimchange`), keep word `aimchangeold` | Candidate (Halo 64's, CC0) |
| X3 | **Unaligned loads and stores** | Address-error crashes the x86 build never has. Ours: grenades near the Flood in The Library (b97–b100), a10's opening cinematic (b115), the first script command, the first network search | Packed data read whole: the script stack's frames start 2 bytes off a word; breakable surfaces' bit vector one byte into its struct (`FIXES_36`, `breakable_surfaces.c#aligned`); recorded-animation event shorts at odd addresses (`FIXES_107`, `recorded_animation_playback.c`); compressed animations' float tables (`FIXES_116`, `model_animations.c#unaligned`); network packets, whose values sit at any offset (`FIXES_PACKET_ALIGNMENT`, `byte_swapping.c`); debug allocations' guard word (`psp_fixups.py`'s `UNALIGNED` table) | Aligned, packed, or read through `PSP_UNALIGNED_*` (`psp_limits.h`, at the repo's root). Found with a strict PPSSPP interpreter, since the emulator's JIT forgives them like x86 (`testing_pipeline.md`) [E] | Candidates one by one (each is small); the packet one changes no bytes on the wire |
| X4 | **The sound cache's page count is fixed** | Sounds read over the memory after the cache; the next map read goes to a garbage address (found replaying fire, melee and grenades) [E] | `SOUND_CACHE_PAGE_COUNT = 1024` (4 KB pages: the Xbox's 4 MB) in `xbox_sound_cache.c`, whatever size the port gives the cache [D] | The page count derived from our cache size. `psp_fixups.py`'s first group, `FIXES` (`xbox_sound_cache.c`) | Candidate (derive it from the size) |

## 3. In ChupathingyCE's Linux platform layer, on a small or slow machine

These are fine on a desktop. They bite when a port reuses `port/linux/src` on small stacks, a FAT card or a limited libc.

| # | Bug | Symptom | Cause | Our fix, where | Upstream? |
|---|---|---|---|---|---|
| P1 | **`CopyFileA`'s 64 KB stack buffer** | A crash saving a new profile (its first save renames it) [M] | A 66 KB stack frame on a 48 KB thread | Heap buffer, 2 KB stack fallback. `FIXES_FRONT` (`xbox_files.c#copybuffer`); commit `21491e2` | Candidate |
| P2 | **`SetEndOfFile` can't shorten through a limited `ftruncate`** | A deleted profile still listed, or the last one listed twice; ~1,000 failed opens in one test [M] | Our libc's `ftruncate` can't shorten a file, so the saved-games index kept its last entry | Shortened by rewriting, for files up to 64 KB. `FIXES_FRONT` (`xbox_files.c#shrink`), keep word `shrinkold` | No (libc-specific); check yours |
| P3 | **Ghost save folders** | A profile name that can never be reused [M] | A save folder with its metadata but no save files (left by P1's crash) holds the name | Such folders removed at start-up and on delete. `FIXES_FRONT` (`xbox_xapi.c#ghosts`, `saved_game_files.c#ghosts`), keep word `ghostskeep` | Maybe |
| P4 | **Case-blind path lookup scans folders** | ~23 s of a 27 s start-up check in storage calls on the PSP (2,285 calls at ~10 ms) [M] | `platform_translate_path` lists each part's parent folder to match names without case, then stats the match, and stats the drive folder on every call | On FAT, which already ignores case, parts are joined as written; each drive folder is made once a run. `FIXES_FRONT` (`xbox_files.c#pathscan`), keep word `pathscan`; commit `a10afbd` | Maybe, behind a "case-blind filesystem" switch |
| P5 | **Two log files held open for the whole run** | The PSP lets a program hold about ten files; two were gone at start-up | The game's own logs opened at start and never closed | Their lines go through a log that opens its file only to write a batch. `FIXES_105` (`errors.c`) | No (platform) |

## 4. Reported by other ports, not seen or fixed by us

From halo-ce-vita's notes (`research_vita.md` §9); credit BirchWoodGod for finding them.

- **Looping sounds keep the old BSP's cluster after a switch** (`sound_manager.c`, `game_sound.c`). Bites only when the sound manager skips frames. A guard to take before any "update sounds less often" change.
- **An uninitialised evasion result** (`path_structure_bsp.c`), kept on purpose in the decomp: with no ground surface, the point's `z` is read unset. On MIPS a NaN `z` fails both comparisons, so the point may be accepted where x86 rejects it [U].
- **`game_sound_restore` reads a looping sound through NULL** after a bad saved-game load.

## Making the next one findable

Most of these showed up because we compare whole game states tick by tick between runs (`portable_speedups.md` §C): G1 and G5 broke that comparison before they broke anything else. halo-ce-vita's method notes (`research_vita.md` §10) list two more sources of run-to-run drift worth masking: uninitialised stack bytes (they build with `-ftrivial-auto-var-init=zero`) and the object marker stamps (`magic_number`).
